# 設計書運用ガイドライン

> **目的**: 言語や運用方式に左右されない設計書を運用し、AIと人間の開発効率を高める。
> **前提**: 設計書は業務の決めごとと構造の判断を書く場所であり、実装の設計図ではない。

---

  * 入手先: [PlantUML core](https://www.npmjs.com/package/@plantuml/core)

## 1. 記述の鉄則（全ドキュメント共通）

* **長文の禁止**: 1文あたり80文字前後を超える文章は禁止する。
  * **カウント基準**: 全角・半角を問わず1字1文字と数える。
  * **対象外**: 表のセル、コードブロック、URLを含む行は数えない。
* **箇条書きの徹底**: 複雑な説明は段落にせず、箇条書きで表現する。
* **簡潔な表現**: 主語と述語を明確にし、冗長な装飾語は削る。
* **重複の禁止**: 同じ規約を2ファイルに書かない。共通仕様書へ切り出す。
* **参照の優先**: 他文書の内容は再掲せず、IDとリンクで参照する。

### 1.1 共通の記載事項

* **先頭**: 1行目に `[一覧へ戻る](相対パス)` を置く。
* **区切り**: 先頭リンクの後に空行、`---`、空行を置く。
* **見出し**: `# [ID] 名称` の形で書く。
* **冒頭**: 見出しの後に空行を置き、文書状態を書く（`確定` または `検討中`）。
* **末尾**: `---`、空行、戻りリンクの順で文書を終える。
* **日付**: 文書に書かない。更新日はGitの履歴で追う。
* **決定者**: その決めごとを決めた部門または担当を書く。
* **未決事項**: 決まっていない論点は明記する。空欄のまま残さない。
* **構成**: 見出しは書く内容に合わせて立てる。定型の雛形は用意しない。

```md
[一覧へ戻る](../INDEX.md)

---

{内容}

---

[一覧へ戻る](../INDEX.md)
```

### 1.2 使う言葉

普段の業務で使われている言葉だけを使う。新しい言葉を作らない。

* **語彙の出どころ**: 用語集（`DEF-000`）に載っている言葉から選ぶ。
* **造語の禁止**: 辞書にない熟語を作らない。漢語を3つ以上つなげない。
* **和語の優先**: 和語で言えることをカタカナ語にしない。
* **カタカナ語の制限**: 業務で口に出して使う言葉だけ許す。3語続いたら書き直す。
* **言い換えの禁止**: 担当者が「返品」と呼ぶものを「返送処理」と書かない。
* **冗長表現の削除**: 「〜という形で」「〜に関して」「〜の観点から」を消す。
* **短縮**: 「〜することができる」は「〜できる」と書く。
* **記号**: 全角ダッシュ（——）は使わない。カッコか読点に置き換える。

**言い換え表**

| 使わない             | 使う            |
| :------------------- | :-------------- |
| 具備する / 保持する  | 持つ / 備える   |
| 実施する / 遂行する  | 行う            |
| 〜を担保する         | 〜を守る        |
| 〜を勘案する         | 〜を考える      |
| 当該〜               | この〜 / その〜 |
| 〜における           | 〜での          |
| 保守性向上化         | 直しやすくする  |
| ユーザー体験の最適化 | 使いやすくする  |
| 逸脱ケース           | 例外            |
| 恒常的に             | いつも / 常に   |

* **確認方法**: 業務担当者に声に出して読んでもらい、引っかかる語を書き直す。

## 2. 用語集（DEF-000）

用語集は設計書として持つ。本ガイドラインには用語を書かない。

* **位置づけ**: 最初に作る設計書。他の設計書より先に作る。
* **場所**: `core/DEF-000_用語集.md`。core直下に置く。IDは `000` で固定する。
* **載せるもの**:
  * 業務の言葉（会員ランク、返品、締め日など）。
  * 業務上の状態の呼び方名（有効、ロック中など）。
  * 設計書を書くための言葉（決めごと、判断の基準、根拠など）。
  * 文書状態の値（`確定`、`検討中`）。この2語以外を文書状態に使わない。
* **載せないもの**:
  * 実装の名前（テーブル名、クラス名、API名）。
  * 国語辞書で足りる一般語。
* **1語の書式**: 用語、定義、使わない言い換え、の3列で書く。
* **使わない言い換え**: 同じものを指す別名を必ず書く。これが表記ゆれの歯止めになる。
* **機械可読の持ち方**: 「使わない言い換え」の列は禁止語チェックの元にする。書式を崩さない。
* **追加のタイミング**: 新しい言葉を使う前に用語集へ足す。設計書の中で定義しない。
* **行数上限**: 対象外とする。分割せず1ファイルで持つ。

### 2.1 最初に作らせるとき

AIに用語集を作らせる場合、次の順で進める。

1. 業務担当者の議事録、既存の資料、問い合わせ文面から言葉を拾わせる。
2. 同じものを指す別名をまとめさせ、どれを使うか担当者に決めてもらう。
3. 決まった語を用語集に、残りを「使わない言い換え」の列に入れる。
4. 以降の設計書作成では、用語集を必ず添えて渡す。

## 3. 書くことと書かないこと

設計書には概念レベルの決めごとと構造の判断を書く。実装の手順は書かない。

| 書くこと                 | 書かないこと                |
| :----------------------- | :-------------------------- |
| 業務上の判断と、その基準 | 関数名、引数、戻り値        |
| その基準を選んだ根拠     | テーブル名、カラム名、API名 |
| 境界の値と、その値の根拠 | 条件分岐の順序、データ構造  |
| 例外の扱い               | エラーコード、ログ出力形式  |
| 状態と、変わるきっかけ   | クラス構成、実装の分け方    |

* **見分け方**: 実装のやり方を変えても、設計書の書き直しが要らないか。
* **状態の呼び方**: 用語集の語で書く。コード上の定数名に合わせない。
* **図の線引き**: 業務レベルの状態遷移図は書いてよい。ER図など実装寄りの図は書かない。

### 3.1 記述例

**NG（実装レベル）**

```text
calculateDiscount(rank, amount) を呼び出す。
rank が "GOLD" の場合、amount * 0.9 を返す。
```

**OK（概念レベル）**

```text
* ゴールド会員には10%の割引を適用する。
  * 根拠: 年間20万円以上の購入を続けてもらうための優遇。
  * 併用: 金額による割引と重ねて適用してよい。
```

### 3.2 言語非依存設計書の追加ルール

方式設計書、インターフェース設計書、DSL仕様書は、言語や運用方式に左右されない決めごとを書く。

| 書くこと | 書かないこと |
| :------- | :----------- |
| データの境界と、越えてはいけない線 | スキーマファイルの中身、型名、フィールド名 |
| DSLの文法規則と、許す組み合わせ | パーサーの実装、ASTの構造 |
| 乱数や時間の扱い方の判断基準 | 乱数生成器の実装名、ライブラリ名 |
| I/O分離の境界と、注入するものの定義 | 通信プロトコル名、DB製品名、OSの機能名 |

* **見分け方**: 言語をTypeScriptからRustに変えても、設計書の書き直しが要らないか。
* **スキーマの扱い**: 設計書（Markdown）にJSONスキーマを直接書かない。`schemas/` に機械可読ファイルとして置く。
* **DSLの語彙**: データ駆動の文法は業務上の言葉で書く。コード上の識別子に合わせない。

## 4. 量の上限

ファイルが太るのを、読んだ印象ではなく行数で止める。

| 種別 | 目安 | 上限 | 超過時の対応 |
| :--------- | :---: | :---: | :-------------------------------------- |
| 方式設計書 | 150行 | 250行 | 構造の判断単位で分割する |
| インターフェース設計書 | 150行 | 250行 | データの種類で分割する |
| DSL仕様書 | 150行 | 250行 | 文法要素の単位で分割する |
| 共通仕様書 | 200行 | 300行 | 分類を細く分ける                      |

* **測定**: `wc -l core/**/*.md` で確認する。
* **原則**: 上限を超えたら「書きすぎ」ではなく「分割漏れ」と考える。
* **例外**: 分けると意味が壊れる場合のみ、冒頭に理由を1行で書く。
* **対象外**: 本書、`INDEX.md`、`DEF-000`、図ファイル、スキーマファイル。

## 5. 粒度の決め方

### 5.1 方式設計（ARC）

* **単位**: 1つの構造的判断を1ファイルとする。
  * 例: I/O分離の原則、決定論の守り方、時間の扱い方。
* **見分け方**: 言語を変えても内容が変わらないか。変わるなら実装の話が混ざっている。
* **大きすぎのサイン**: 概要が「〜と〜を行う」と接続詞でつながる。
* **細かすぎのサイン**: 単独では意味をなさず、他と必ずセットで読む。

### 5.2 決めごと（BIZ）

* **単位**: 業務担当者が「1つの決めごと」と認識するまとまり。
* **見分け方**: そのファイルだけを担当者に見せて、合っているか判断してもらえるか。
* **大きすぎのサイン**: 概要が「〜と〜を行う」と接続詞でつながる。
* **細かすぎのサイン**: 単独では意味をなさず、他と必ずセットで読む。
* **注意**: 実装の分け方に合わせない。コードの構成が変わっても分け直さない。

### 5.3 インターフェース設計（INT）

* **単位**: 1つのデータ境界を1ファイルとする。
  * 例: 操作の定義、事象の定義、状態の定義、公開と非公開の境界。
* **見分け方**: エンジンと外部との間で、どのデータをやり取りするかの判断が1つに絞れているか。
* **大きすぎのサイン**: 複数のデータ種類が同じファイルに入っている。

### 5.4 DSL仕様（DSL）

* **単位**: 1つの文法要素を1ファイルとする。
  * 例: ルールの定義、条件の定義、操作の定義、状態遷移の定義、出力の定義。
* **見分け方**: 1つの文法要素について、業務担当者が「これだけで判断できる」と納得できるか。
* **大きぎのサイン**: 複数の文法要素が同じファイルに入っている。

## 6. 基本方針

言語非依存の構造、データの境界、文法規則の3層で管理する。

| 種別 | 配置先 | 主な役割 | 記述しないこと |
| :------------- | :--------------- | :--------------------------------- | :----------------------- |
| **方式設計書** | `core/arch/` | 言語非依存の構造、I/O分離、決定論の守り方 | 言語名、フレームワーク名、ライブラリ名 |
| **インターフェース設計書** | `core/interface/` | エンジンと外部とのデータの受け渡しの境界 | 関数名、引数、戻り値、通信プロトコル名 |
| **DSL仕様書** | `core/dsl/` | データで動く仕様の文法規則 | パーサーの実装、コード生成の手順 |
| **共通仕様書** | `core/common/` | 全体規約、設計書全体の共通ルール | 個別構造や文法の事情 |

* **共通仕様書に置くもの**: 入力チェックの書式、エラー表示の統一ルール、権限の区分、日付や金額の書き方。
* **用語集の扱い**: 内容は共通層に属するが、ファイルは `core` 直下に固定で置く（§2）。
* **移す目安**: 3ファイル以上に同じ記述が出たら共通仕様書へ移す。
* **機械可読スキーマの扱い**: 設計書（Markdown）と分離し、`schemas/` に置く。設計書には境界の定義と考え方を書く。

## 7. ファイル命名規則

### 7.1 フォーマット

* **方式設計書**: `ARC-{3桁数字}_{構造名}.md`
* **インターフェース設計書**: `INT-{3桁数字}_{境界名}.md`
* **DSL仕様書**: `DSL-{3桁数字}_{文法要素名}.md`
* **共通仕様書**: `COM-{3桁数字}_{分類名}.md`
* **用語集**: `DEF-000_用語集.md`

### 7.2 命名ルール

* **ID指定**: 3桁の連番（`001`, `002`, ...）を使用する。
* **予約ID**: `DEF-000` は用語集に固定する。他に割り当てない。
* **区切り文字**: IDと名称の間はアンダースコア `_` で区切る。
* **ファイル名**: スペースを含めず、業務で通じる日本語の名詞にする。
* **動詞の回避**: 「〜処理」「〜判定」より「〜ルール」「〜基準」「〜定義」を選ぶ。
* **ID再利用の禁止**: 廃止したIDは番号のまま残し、新しく割り当てない。
* **例**:
  * 方式: `ARC-001_IO分離原則.md`
  * インターフェース: `INT-001_操作の定義.md`
  * DSL: `DSL-001_ルールの定義.md`
  * 共通: `COM-001_入力チェック規約.md`

### 8.1 設計書以外のファイル（図・画像）

画像やUML図など、Markdown以外のファイルの置き場所と取り込み方を定める。

* **置き場所**: 種別ごとのディレクトリ（`arch/` 等）の直下に `res/` を作って置く。
* **共通図**: 複数種別で使う図は `common/res/` に置く。
* **画像**: `res/img/` に置く。
* **図ソース**: 図は形式ごとの場所に1図1ファイルで置く。
  * PlantUML は `res/uml/` に置く。ファイルは `{図の概要}.uml`。
  * Mermaid は `res/mmd/` に置く。ファイルは `{図の概要}.mmd`。
* **変換後の図**: ソースと同じ形式の場所に SVG を置く。
  * PlantUML は `res/uml/svg/`。
  * Mermaid は `res/mmd/svg/`。
* **取り込み**: 本文には SVG を画像で参照する。
  * 例: `![状態遷移](res/uml/svg/state_flow.svg)`
* **変換**: ソースを直したら SVG を作り直す。SVG を直接直さない。
* **分割の原則**: 図は必ず別ファイルにする。Markdown本文へ図の定義を直接書かない。
* **作る範囲**: 実際にファイルを置く種別にだけ `res/` を作る。空のまま用意しない。
* **参照パス**: 相対パスで書く。
  * 例: `res/uml/svg/state_flow.svg`
  * 例: `res/mmd/svg/state_flow.svg`
* **ファイル名**: 設計書のIDに合わせなくてよい。図の中身が分かる名前を付ける。

### 8.2 機械可読スキーマとテスト資産

設計書（Markdown）と機械可読ファイルは分離する。

* **スキーマの置き場所**: `schemas/` に置く。
* **スキーマの形式**: JSON Schema や Protocol Buffers 等、言語非依存の形式を使う。
* **設計書との関係**: 設計書（INT / DSL）には「どのようなデータの境界を定めるか」を書く。スキーマファイルには「その中身」を書く。
* **テスト資産の置き場所**: `tests/golden/` 等に置く。
* **テスト資産の形式**: JSON 等、言語非依存の形式を使う。
* **テストの書き分け**: ARCやINTに検証観点を書き、ファイルに具体例を書く。
* **自動生成**: スキーマから型定義コードを自動生成してもよい。生成物は設計書ではない。

## 9. 参照ルール

* **ARC → BIZ / COM**: 業務上の決めごとが構造に影響する場合はリンクする。
* **INT → ARC**: データの境界は方式設計の構造に従う。
* **DSL → BIZ / ARC**: データ駆動の文法は業務ルールと構造規約に従う。
* **INT → DSL**: 処理の実行に必要なデータの受け渡しが関わる場合はリンクする。
* **BIZ → INT / DSL / ARC**: 書かない。業務の決めごとは実装の有無に左右されない。
* **全設計書 → INDEX**: 先頭と末尾に戻りリンクを置く。
* **INDEX → 各設計書**: 各行のIDを `[ID](相対パス)` でリンクする。
* **用語集への参照**: 個別には書かない。全設計書に当然に適用する。
* **循環参照**: 許す。読み手は困らない。
* **禁じるのは重複だけ**: 同じ内容が2箇所にあると、片方が古くなる。
* **リンク形式**: `[表示文字](相対パス)` で書く。
  * `![]()` は画像の表示に使い、リンクには使わない。
  * 相対パスを使い、パスをコードで囲まない。

### 9.1 逆引き（INDEX.md）

* **役割**: どの設計書がどの決めごとを使うかを1枚で管理する。
* **理由**: 方式設計書に他の設計書のIDを書くと、設計書が増減するたびに方式設計書を触ることになる。
* **主語の固定**: 1行を1設計書とする。関連する他の設計書IDを関連IDに列挙する。
* **並べる範囲**: 方式設計・インターフェース設計・DSL仕様・共通仕様の表を並べる。
* **リンク**: 各行のIDを `[ID](相対パス)` で設計書へリンクする。
* **形式**: ID、名称、文書状態、関連IDの列とする。
* **更新**: 新規作成、廃止、名称変更のたびに更新する。

## 10. 変更・廃止の運用

### 10.1 変更

* **順序**: 仕様を変えるときは、コードより先に設計書を直す。
* **影響の確認**: 直す前に `grep -r "対象ID" core/` と `INDEX.md` で関連を調べる。
* **言葉の変更**: 呼び名を変えるときは用語集を先に直し、旧称を「使わない言い換え」へ移す。
* **実装都合の変更**: コードの構成を変えただけでは設計書を触らない。触る必要が出たら粒度を疑う。
* **スキーマの変更**: 設計書（INT / DSL）を直したら、対応する機械可読スキーマファイルも直す。
* **方式の変更**: 言語を変えただけでは方式設計書（ARC）を触らない。触る必要が出たらI/O分離や決定論の境界を疑う。

### 10.2 廃止

廃止は文書状態では表さない。アーカイブへ移すことで表す。

* **手順**:
  1. `INDEX.md` で関連が0件であることを確認する。
  2. ファイルを `core/archive/` へ移す。
  3. `INDEX.md` から該当行を消す。
* **IDの扱い**: 欠番のまま残し、使い回さない。
* **用語集**: 廃止しない。使わなくなった語は「使わない言い換え」に残す。
* **スキーマの廃止**: 設計書を廃止したら、対応する機械可読スキーマファイルも `archive/` へ移すか、または削除の判断をする。

## 13. 言語非依存設計の鉄則

言語や運用方式に左右されない設計書の追加ルール。

### 13.1 I/O分離

* **原則**: コアエンジンは外部入出力を持たない。
* **外部入出力の例**: 通信、DBアクセス、OSタイマー、描画、ファイル読み書き。
* **注入の方法**: 外部から「操作」または「時間の経過」を表すデータを受け取る。
* **出力の方法**: コアエンジンは「新しい状態」と「発生した事象」の一覧を返すだけにする。
* **境界**: 方式設計書（ARC）に「何を注入し、何を返すか」の境界を書く。インターフェース設計書（INT）に「そのデータの中身」の概念を書く。

### 13.2 決定論

* **原則**: 同じ入力を与えれば、どの言語でも同じ結果になる。
* **乱数**: 言語標準の乱数を使わない。内部状態を持つ擬似乱数を使う。
* **時間**: OSのタイマーを使わない。時間の経過は外部から注入する。
* **状態の含む範囲**: 乱数生成器の内部状態も、状態の中に含める。
* **境界**: 方式設計書（ARC）に「乱数と時間の扱い方の判断基準」を書く。

### 13.3 データとロジックの分離

* **原則**: 変化しうる仕様はDSL（データ）として定義し、エンジンは解釈する。
* **DSLの定義**: DSL仕様書（DSL）に「文法規則と、許す組み合わせ」を書く。
* **データの置き場所**: 実装に依存しない形で持つ。
* **境界**: DSL仕様書（DSL）に「ルール、条件、操作、状態遷移、出力」の定義を書く。

### 13.4 スキーマとテスト資産の分離

* **原則**: 設計書（Markdown）に機械可読なスキーマを直接書かない。
* **スキーマの置き場所**: `schemas/` に置く。
* **設計書の役割**: 「どのようなデータの境界を定めるか」「どのような観点でテストするか」を書く。
* **機械可読ファイルの役割**: 「具体的な型定義」「具体的な入出力組み合わせ」を書く。
* **自動生成**: スキーマから型定義コードを自動生成してもよい。生成物は設計書ではない。

### 13.5 設計書と実装の分離

* **原則**: 設計書は「言語を変えても書き直しが要らない内容」にする。
* **確認方法**: 「TypeScriptからRustに変えた場合、この設計書を直す必要があるか」を問う。
* **直す必要がある場合**: 実装の話が混ざっている。方式設計書（ARC）かインターフェース設計書（INT）かDSL仕様書（DSL）の粒度を疑う。
