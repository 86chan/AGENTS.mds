# 設計書運用ガイドライン

> **目的**: 言語や運用方式に左右されない設計書を運用し、AIと人間の開発効率を高める。
> **前提**: 設計書は構造の判断を書く場所であり、業務の決めごとは specs/BIZ を参照する。実装の設計図ではない。

## 1. 記述の鉄則（全ドキュメント共通）

共通ルールは [COMMON §1](../COMMON.md) を参照。本ガイドライン固有の追加ルールのみ以下に記す。

* **言語非依存の徹底**: 言語名、フレームワーク名、ライブラリ名を書かない（§3.2 で詳述）。
* **実装レベルの排除**: 関数名、引数、戻り値、テーブル名、カラム名、API名を書かない。

## 2. 用語集（DEF-000）

運用ルールは [COMMON §2](../COMMON.md) を参照。core固有の追加事項:

* **場所**: `core/DEF-000_用語集.md`。core直下に置く。IDは `000` で固定する。
* **載せる語の種類**: 業務の言葉、業務上の状態の呼び名、設計書を書くための言葉、文書状態の値。
* **載せないもの**: 実装の名前（テーブル名、クラス名、API名）、国語辞書で足りる一般語。

## 3. 書くことと書かないこと

設計書には概念レベルの決めごとと構造の判断を書く。実装の手順は書かない。

| 書くこと                 | 書かないこと                |
| :----------------------- | :-------------------------- |
| 非機能の方式（性能、安全、監視） | 非機能の目標値、実現手段 |
| 境界の値と、その値の根拠 | 条件分岐の順序、データ構造  |
| 例外の扱い               | エラーコード、ログ出力形式  |
| 状態と、変わるきっかけ   | クラス構成、実装の分け方    |

* **見分け方**: 実装のやり方を変えても、設計書の書き直しが要らないか。
* **状態の呼び方**: 用語集の語で書く。コード上の定数名に合わせない。
* **図の線引き**: 業務レベルの状態遷移図は書いてよい。ER図など実装寄りの図は書かない。

### 3.1 記述例

**NG（実装レベル）**

```text
calculateDiscount(rank, amount) を呼び出す。
rank が "GOLD" の場合、amount * 0.9 を返す。
```

**OK（概念レベル）**

```text
* ゴールド会員には10%の割引を適用する。
  * 根拠: 年間20万円以上の購入を続けてもらうための優遇。
  * 併用: 金額による割引と重ねて適用してよい。
```

### 3.2 言語非依存設計書の追加ルール

方式設計書、インターフェース設計書、DSL仕様書は、言語や運用方式に左右されない決めごとを書く。

| 書くこと | 書かないこと |
| :------- | :----------- |
| データの境界と、越えてはいけない線 | スキーマファイルの中身、型名、フィールド名 |
| DSLの文法規則と、許す組み合わせ | パーサーの実装、ASTの構造 |
| 乱数や時間の扱い方の判断基準 | 乱数生成器の実装名、ライブラリ名 |
| I/O分離の境界と、注入するものの定義 | 通信プロトコル名、DB製品名、OSの機能名 |

* **見分け方**: 言語をTypeScriptからRustに変えても、設計書の書き直しが要らないか。
* **スキーマの扱い**: 設計書（Markdown）にJSONスキーマを直接書かない。`schemas/` に機械可読ファイルとして置く。
* **DSLの語彙**: データ駆動の文法は業務上の言葉で書く。コード上の識別子に合わせない。

## 4. 量の上限

ファイルが太るのを、読んだ印象ではなく行数で止める。

| 種別 | 目安 | 上限 | 超過時の対応 |
| :--------- | :---: | :---: | :-------------------------------------- |
| 方式設計書 | 150行 | 250行 | 構造の判断単位で分割する |
| インターフェース設計書 | 150行 | 250行 | データの種類で分割する |
| DSL仕様書 | 150行 | 250行 | 文法要素の単位で分割する |
| 共通仕様書 | 200行 | 300行 | 分類を細く分ける                      |

* **測定**: `wc -l core/**/*.md` で確認する。
* **原則**: 上限を超えたら「書きすぎ」ではなく「分割漏れ」と考える。
* **例外**: 分けると意味が壊れる場合のみ、冒頭に理由を1行で書く。
* **対象外**: 本書、`INDEX.md`、`DEF-000`、図ファイル、スキーマファイル。

## 5. 粒度の決め方

### 5.1 方式設計（ARC）

* **単位**: 1つの構造的判断を1ファイルとする。
  * 例: I/O分離の原則、決定論の守り方、時間の扱い方。
* **見分け方**: 言語を変えても内容が変わらないか。変わるなら実装の話が混ざっている。
* **大きすぎのサイン**: 概要が「〜と〜を行う」と接続詞でつながる。
* **細かすぎのサイン**: 単独では意味をなさず、他と必ずセットで読む。

### 5.2 決めごと（BIZ）

BIZ の粒度は specs/Specs.md §5.2 を参照。core は BIZ を定義せず、specs/BIZ-xxx を参照する。

### 5.3 インターフェース設計（INT）

* **単位**: 1つのデータ境界を1ファイルとする。
  * 例: 操作の定義、事象の定義、状態の定義、公開と非公開の境界。
* **見分け方**: エンジンと外部との間で、どのデータをやり取りするかの判断が1つに絞れているか。
* **大きすぎのサイン**: 複数のデータ種類が同じファイルに入っている。

### 5.4 DSL仕様（DSL）

* **単位**: 1つの文法要素を1ファイルとする。
  * 例: ルールの定義、条件の定義、操作の定義、状態遷移の定義、出力の定義。
* **見分け方**: 1つの文法要素について、業務担当者が「これだけで判断できる」と納得できるか。
* **大きすぎのサイン**: 複数の文法要素が同じファイルに入っている。

## 6. 基本方針

言語非依存の構造、データの境界、文法規則の3層で管理する。

| 種別 | 配置先 | 主な役割 | 記述しないこと |
| :------------- | :--------------- | :--------------------------------- | :----------------------- |
| **方式設計書** | `core/arch/` | 言語非依存の構造、I/O分離、決定論の守り方 | 言語名、フレームワーク名、ライブラリ名 |
| **インターフェース設計書** | `core/interface/` | エンジンと外部とのデータの受け渡しの境界 | 関数名、引数、戻り値、通信プロトコル名 |
| **DSL仕様書** | `core/dsl/` | データで動く仕様の文法規則 | パーサーの実装、コード生成の手順 |
| **共通仕様書** | `core/common/` | 全体規約、設計書全体の共通ルール | 個別構造や文法の事情 |

* **共通仕様書に置くもの**: 入力チェックの書式、エラー表示の統一ルール、権限の区分、日付や金額の書き方。
* **用語集の扱い**: 内容は共通層に属するが、ファイルは `core` 直下に固定で置く（§2）。
* **移す目安**: 3ファイル以上に同じ記述が出たら共通仕様書へ移す。
* **機械可読スキーマの扱い**: 設計書（Markdown）と分離し、`schemas/` に置く。設計書には境界の定義と考え方を書く。

## 7. ファイル命名規則

### 7.1 フォーマット

* **方式設計書**: `ARC-{3桁数字}_{構造名}.md`
* **インターフェース設計書**: `INT-{3桁数字}_{境界名}.md`
* **DSL仕様書**: `DSL-{3桁数字}_{文法要素名}.md`
* **共通仕様書**: `COM-{3桁数字}_{分類名}.md`
* **用語集**: `DEF-000_用語集.md`

### 7.2 命名ルール

* **ID指定**: 3桁の連番（`001`, `002`, ...）を使用する。
* **予約ID**: `DEF-000` は用語集に固定する。他に割り当てない。
* **区切り文字**: IDと名称の間はアンダースコア `_` で区切る。
* **ファイル名**: スペースを含めず、業務で通じる日本語の名詞にする。
* **動詞の回避**: 「〜処理」「〜判定」より「〜ルール」「〜基準」「〜定義」を選ぶ。
* **ID再利用の禁止**: 廃止したIDは番号のまま残し、新しく割り当てない。
* **例**:
  * 方式: `ARC-001_IO分離原則.md`
  * インターフェース: `INT-001_操作の定義.md`
  * DSL: `DSL-001_ルールの定義.md`
  * 共通: `COM-001_入力チェック規約.md`

### 8.1 設計書以外のファイル（図・画像）

図・画像の扱いは [COMMON §3](../COMMON.md) を参照。

### 8.2 機械可読スキーマとテスト資産

設計書（Markdown）と機械可読ファイルは分離する。

* **スキーマの置き場所**: `schemas/` に置く。
* **スキーマの形式**: JSON Schema や Protocol Buffers 等、言語非依存の形式を使う。
* **設計書との関係**: 設計書（INT / DSL）には「どのようなデータの境界を定めるか」を書く。スキーマファイルには「その中身」を書く。
* **テスト資産の置き場所**: `tests/golden/` 等に置く。
* **テスト資産の形式**: JSON 等、言語非依存の形式を使う。
* **テストの書き分け**: ARCやINTに検証観点を書き、ファイルに具体例を書く。
* **自動生成**: スキーマから型定義コードを自動生成してもよい。生成物は設計書ではない。

## 9. 参照ルール

* **ARC → specs/BIZ, COM**: 業務上の決めごとが構造に影響する場合はリンクする。
* **INT → ARC**: データの境界は方式設計の構造に従う。
* **DSL → BIZ / ARC**: データ駆動の文法は業務ルールと構造規約に従う。
* **INT → DSL**: 処理の実行に必要なデータの受け渡しが関わる場合はリンクする。
* **BIZ → INT / DSL / ARC**: 書かない。業務の決めごとは実装の有無に左右されない。

## 10. 変更・廃止の運用

### 10.1 変更

共通ルールは [COMMON §5.1](../COMMON.md) を参照。core固有: 設計書（INT / DSL）を変更したら、対応する `core/schemas/` のスキーマも直す。方式変更時はI/O分離・決定論の境界を疑う。影響確認は `grep -r "対象ID" core/ impl/`。

### 10.2 廃止

共通ルールは [COMMON §5.2](../COMMON.md) を参照。core固有: アーカイブ先は `core/archive/`。スキーマも `core/schemas/` から `archive/` へ移すか削除判断。

## 11. レビューチェックリスト

共通のチェック項目は [COMMON §7](../COMMON.md) を参照。以下は core 固有。

設計書の変更後、マージ前とチェックイン前に `markdownlint-cli2`, `@sourcemeta/jsonschema` を実行する。
エラーを直し、自動判定できない項目を目で確認する。

- [ ] 言語名、フレームワーク名、ライブラリ名が混ざっていないか（ARC / INT / DSL）
- [ ] スキーマの中身が設計書に直接書かれていないか（`schemas/` に分離しているか）
- [ ] DSLの文法が業務上の言葉で書かれているか
- [ ] I/O分離の境界が明確に書かれているか（ARC）
- [ ] 非機能の方式が混入していないか（目標値は specs、実現手段は impl）
- [ ] 設計書を直したら、対応する機械可読スキーマも直しているか

**目視チェック（人が判断）**

- [ ] 方式設計書に実装の手順が混ざっていないか
- [ ] インターフェース設計書に通信プロトコル名が混ざっていないか
- [ ] DSL仕様書にパーサーの実装が混ざっていないか
- [ ] 言語を変えても書き直しが要らない内容になっているか（ARC / INT / DSL）

## 13. 言語非依存設計の鉄則

言語や運用方式に左右されない設計書の追加ルール。

### 13.1 I/O分離

* **原則**: コアエンジンは外部入出力を持たない。
* **外部入出力の例**: 通信、DBアクセス、OSタイマー、描画、ファイル読み書き。
* **注入の方法**: 外部から「操作」または「時間の経過」を表すデータを受け取る。
* **出力の方法**: コアエンジンは「新しい状態」と「発生した事象」の一覧を返すだけにする。
* **境界**: 方式設計書（ARC）に「何を注入し、何を返すか」の境界を書く。インターフェース設計書（INT）に「そのデータの中身」の概念を書く。

### 13.2 決定論

* **原則**: 同じ入力を与えれば、どの言語でも同じ結果になる。
* **乱数**: 言語標準の乱数を使わない。内部状態を持つ擬似乱数を使う。
* **時間**: OSのタイマーを使わない。時間の経過は外部から注入する。
* **状態の含む範囲**: 乱数生成器の内部状態も、状態の中に含める。
* **境界**: 方式設計書（ARC）に「乱数と時間の扱い方の判断基準」を書く。

### 13.3 データとロジックの分離

* **原則**: 変化しうる仕様はDSL（データ）として定義し、エンジンは解釈する。
* **DSLの定義**: DSL仕様書（DSL）に「文法規則と、許す組み合わせ」を書く。
* **データの置き場所**: 実装に依存しない形で持つ。
* **境界**: DSL仕様書（DSL）に「ルール、条件、操作、状態遷移、出力」の定義を書く。

### 13.4 スキーマとテスト資産の分離

* **原則**: 設計書（Markdown）に機械可読なスキーマを直接書かない。
* **スキーマの置き場所**: `schemas/` に置く。
* **設計書の役割**: 「どのようなデータの境界を定めるか」「どのような観点でテストするか」を書く。
* **機械可読ファイルの役割**: 「具体的な型定義」「具体的な入出力組み合わせ」を書く。
* **自動生成**: スキーマから型定義コードを自動生成してもよい。生成物は設計書ではない。

### 13.5 設計書と実装の分離

* **原則**: 設計書は「言語を変えても書き直しが要らない内容」にする。
* **確認方法**: 「TypeScriptからRustに変えた場合、この設計書を直す必要があるか」を問う。
* **直す必要がある場合**: 実装の話が混ざっている。方式設計書（ARC）かインターフェース設計書（INT）かDSL仕様書（DSL）の粒度を疑う。業務判断が混ざっている場合は specs/BIZ へ移す。
