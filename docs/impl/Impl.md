# 設計書運用ガイドライン

> **目的**: 言語非依存の詳細設計を、言語固有のコード構造へ写像する実装設計を運用し、AIと人間の開発効率を高める。
> **前提**: 実装設計は詳細設計（core）の判断をコード構造に翻訳する場所であり、設計の根拠や業務判断は書かない。

---

### 0 ツール一覧

使うツールと入手先を並べる。ドキュメントを整備するためのツールのみを扱う。

* **PlantUML**: JS 版の `@plantuml/core` を使う。
  * 用途: `.uml` を SVG に変換する。
  * 入手先: [PlantUML core](https://www.npmjs.com/package/@plantuml/core)
* **Mermaid**: `@mermaid-js/mermaid-cli` を使う。
  * 用途: `.mmd` を SVG に変換する。
  * 入手先: [Mermaid CLI](https://www.npmjs.com/package/@mermaid-js/mermaid-cli)
* **markdownlint**: `markdownlint-cli2` を使う。
  * 用途: 記述ルールを機械で確かめる。
  * 入手先: [markdownlint-cli2](https://www.npmjs.com/package/markdownlint-cli2)
* **jsonschemalint**: `@sourcemeta/jsonschema` を使う。
  * 用途: 記述ルールを機械で確かめる。
  * 入手先: [JSON Schema CLI](https://www.npmjs.com/package/@sourcemeta/jsonschema)

## 1. 記述の鉄則（全ドキュメント共通）

`core/Core.md` §1 および `specs/Specs.md` §1 の記述の鉄則を踏襲する。

* **長文の禁止**: 1文あたり80文字前後を超える文章は禁止する。
* **箇条書きの徹底**: 複雑な説明は段落にせず、箇条書きで表現する。
* **簡潔な表現**: 主語と述語を明確にし、冗長な装飾語は削る。
* **重複の禁止**: 同じ規約を2ファイルに書かない。共通仕様書へ切り出す。
* **参照の優先**: 他文書の内容は再掲せず、IDとリンクで参照する。

### 1.1 共通の記載事項

`core/Core.md` §1.1 を踏襲する。

* **先頭**: 1行目に `[一覧へ戻る](相対パス)` を置く。
* **区切り**: 先頭リンクの後に空行、`---`、空行を置く。
* **見出し**: `# [ID] 名称` の形で書く。
* **冒頭**: 見出しの後に空行を置き、文書状態を書く（`確定` または `検討中`）。
* **末尾**: `---`、空行、戻りリンクの順で文書を終える。
* **日付**: 文書に書かない。更新日はGitの履歴で追う。
* **決定者**: その決めごとを決めた部門または担当を書く。
* **未決事項**: 決まっていない論点は明記する。空欄のまま残さない。

## 2. 書くことと書かないこと

実装設計にはコード構造の判断を書く。業務判断と業務上の根拠は書かない。技術選定の理由・代替案・トレードオフは書く。

| 書くこと | 書かないこと |
| :--- | :--- |
| モジュール・パッケージ構成 | 業務上の判断と、その基準 |
| クラス・関数の割り当て（公開境界） | 判断の基準を選んだ根拠（業務レベル） |
| フレームワーク・ライブラリの選定と、その理由・代替案 | 境界の値と、その値の根拠 |
| 具体アダプタと配線（composition root、DI） | 状態と、変わるきっかけ |
| 言語非依存設計から実装への写像 | DSLの文法規則 |
| 言語固有の制約と、その対処 | I/O分離の境界の定義 |
| 設定・エラー変換・DB/API名 | 業務上の状態遷移 |
| 非機能の実現手段（性能、安全、監視） | 非機能の目標値 |
| ビルド・テスト構成 | |

- **見分け方**: 言語を変えたら、この文書を書き直す必要があるか。必要なら実装設計の話。不要ならcoreへ移す。
- **状態の呼び方**: 用語集の語で書く。識別子は命名規約に従う。

## 2.1 写像表（必須）

各実装設計書には、言語非依存設計から実装への写像を表で示す。

| core ID（節） | specs ID | モジュールパス | 公開入口 | 状態 | 検証方法 |
| :--- | :--- | :--- | :--- | :--- | :--- |

- **状態**: `実装済` / `未実装` / `対象外` のいずれかを書く。未実装と対象外は明示的に残す。
- **core IDの網羅**: `impl/{lang}/INDEX.md` で、参照すべきcore IDの網羅率を確認する。
- **検証方法**: テスト名、ゴールデンケース、または手動確認のいずれかを書く。

## 3. 分量の上限

ファイルが太るのを、読んだ印象ではなく行数で止める。

| 種別 | 目安 | 上限 | 超過時の対応 |
| :--- | :---: | :---: | :--- |
| 実装設計書 | 150行 | 250行 | モジュール単位で分割する |

- **測定**: `wc -l impl/**/*.md` で確認する。
- **原則**: 上限を超えたら「書きすぎ」ではなく「分割漏れ」と考える。
- **対象外**: 本ガイドライン、`INDEX.md`、用語集（`DEF-000`）。

---

## 4. 粒度の決め方

- **単位**: 1つのモジュールまたは1つのサブシステムを1ファイルとする。
- **見分け方**: そのファイルだけを実装者に見せて、コード構造を判断してもらえるか。
- **大きすぎのサイン**: 概要が「〜と〜を行う」と接続詞でつながる。
- **細かすぎのサイン**: 単独では意味をなさず、他と必ずセットで読む。

---

## 5. 基本方針

実装設計は、core（詳細設計）の言語非依存判断を、言語固有のコード構造に写像する層。

| 種別 | 配置先 | 主な役割 | 記述しないこと |
| :--- | :--- | :--- | :--- |
| 実装設計書 | `impl/` | モジュール構成、クラス割り当て、フレームワーク選定 | 業務判断、I/O分離の境界定義 |

- **coreとの関係**: coreの方式設計書（ARC）・インターフェース設計書（INT）・DSL仕様書（DSL）を前提とする。写像の根拠としてIDで参照する。
- **specsとの関係**: specsの画面・業務仕様を実装に落とし込む際の制約として参照する。
- **言語の選定**: 実装設計書群は言語ごとに `impl/{lang}/` に分ける。1つのディレクトリに複数言語を併記しない。同一言語で複数アプリがある場合は、システム単位でさらに分割する。

---

## 6. ファイル命名規則

- **実装設計書**: `impl/{lang}/IMP-{3桁数字}_{モジュール名}.md`
- **用語集**: `impl/{lang}/DEF-000_用語集.md`（言語ディレクトリ直下に固定）

- **ID指定**: 3桁の連番（`001`, `002`, ...）を使用する。連番は言語ディレクトリごとに独立する。
- **予約ID**: `DEF-000` は用語集に固定する。他に割り当てない。
- **区切り文字**: IDと名称の間はアンダースコア `_` で区切る。
- **ファイル名**: スペースを含めず、実装者に通じる日本語の名詞にする。
- **ID再利用の禁止**: 廃止したIDは欠番のまま残し、新しく割り当てない。

## 7. ディレクトリ構造

```
impl/
├── INDEX.md                  # 全言語の実装設計書の一覧
├── {lang}/                   # 言語ごとの実装設計書群
│   ├── INDEX.md              # その言語の実装設計書の一覧
│   ├── DEF-000_用語集.md     # その言語の技術用語集
│   ├── IMP-001_モジュール構成.md
│   ├── ...
│   ├── res/
│   │   ├── uml/
│   │   │   └── svg/
│   │   └── mmd/
│   │       └── svg/
│   └── archive/
└── archive/                  # 廃止済み言語群
```

- **図・画像**: `impl/res/` に置く。PlantUMLは `res/uml/`（ソース）と `res/uml/svg/`（変換後）。Mermaidは `res/mmd/` と `res/mmd/svg/`。
- **INDEXの必須化**: 言語ディレクトリごとに `INDEX.md` を必ず置く。全言語を横断する `impl/INDEX.md` は任意とする。
- **取り込み**: 本文には SVG を画像で参照する。
- **変換**: ソースを直したら SVG を作り直す。SVG を直接直さない。
- **作る範囲**: 実際にファイルを置く場合にだけ `res/` を作る。空のまま用意しない。

## 8. 参照ルール

- **IMP → core (ARC / INT / DSL)**: 写像の根拠となる方式・境界・文法をIDで参照する。IDは `core/ARC-001` のように完全修飾し、節番号まで書く。
- **IMP → specs (SCR / BIZ)**: 実装対象の画面・業務仕様をIDで参照する。IDは `specs/SCR-001` のように完全修飾する。
- **IMP → 言語AGENTS.md**: コーディング規約・命名規則の根拠を参照する。
- **core → IMP**: 書かない。詳細設計は実装の有無に左右されない。
- **specs → IMP**: 書かない。基本設計は実装の有無に左右されない。
- **全実装設計書 → INDEX**: 先頭と末尾に戻りリンクを置く。
- **INDEX → 各実装設計書**: 各行のIDを `[ID](相対パス)` でリンクする。
- **循環参照**: 許す。読み手は困らない。
- **禁じるのは重複だけ**: 同じ内容が2箇所にあると、片方が古くなる。
- **リンク形式**: `[表示文字](相対パス)` で書く。

### 逆引き（INDEX.md）

- **役割**: どの実装設計書がどの詳細設計・基本設計を使うかを1枚で管理する。
- **主語の固定**: 1行を1実装設計書とする。関連するcore / specsのIDを関連IDに列挙する。
- **形式**: ID、名称、文書状態、関連IDの列とする。
- **更新**: 新規作成、廃止、名称変更のたびに更新する。

## 9. 変更・廃止の運用

### 変更

- **順序**: 実装を変えるときは、実装設計書を先に直す。設計書（core / specs）の変更が必要なら、そちらを先に直す。
- **影響の確認**: 直す前に `grep -r "対象ID"` と `INDEX.md` で関連を調べる。core/specs は impl を参照しない。impl 側の影響は `grep -r "対象ID" impl/` で確認する。
- **言語の変更**: 言語を変えるときは `impl/{lang}/` を新規作成する。既存の言語群は `impl/archive/` へ移す。IDの連番は新言語群で独立して採番する。
- **coreの変更**: coreの方式設計が変わったら、影響を受ける実装設計書を直す。
- **変更トリガー**: モジュール境界、依存方向、公開契約、DI、フレームワークが変わったときのみ実装設計書を更新する。内部リファクタは対象外。
- **状態ゲート**: 参照するcoreが `検討中` の間、impl を `確定` にしない。

### 廃止

廃止は文書状態では表さない。アーカイブへ移すことで表す。

1. `INDEX.md` で関連が0件であることを確認する。
2. ファイルを `archive/` へ移す。
3. `INDEX.md` から該当行を消す。

- **IDの扱い**: 欠番のまま残し、使い回さない。
- **用語集**: 廃止しない。使わなくなった語は「使わない言い換え」に残す。

## 10. 言語非依存設計との境界

実装設計に書いてよいものと、coreへ書くべきものの境界。

- **実装設計に書く**: モジュール名、クラス名、関数名、フレームワーク名、ライブラリ名、ビルドツール名、ディレクトリ構成、依存関係、具体アダプタと配線（composition root、DI）、設定、エラー変換、DB/API名、非機能の実現手段。
- **coreに書く**: I/O分離の境界、決定論の守り方、DSLの文法規則、乱数・時間の扱い方の判断基準。
- **見分け方**: 「TypeScriptからRustに変えた場合、この文書を直す必要があるか」を問う。直す必要があるなら実装設計。不要ならcore。

- **根拠の扱い**: 業務判断の根拠は書かない。技術選定の理由・代替案・トレードオフは書く。詳細な比較検討は ADR に委ねる。
- **非機能の役割分担**: 目標値はspecs、方式はcore、実現手段はimpl。

## 11. レビューチェックリスト

- [ ] 行数が上限内か（`wc -l`）
- [ ] 1文が80文字以内か（表・コード・URL行を除く）
- [ ] 用語集の「使わない言い換え」が混ざっていないか
- [ ] coreのIDを参照し、根拠を明示しているか
- [ ] 写像表を記載しているか
- [ ] 未実装・対象外を明示しているか
- [ ] 言語固有の詳細がcoreに混入していないか
- [ ] 設計の根拠・業務判断が混入していないか
- [ ] 各実装設計書の先頭と末尾に INDEX へのリンクがあるか
- [ ] INDEX の各行が実装設計書へのリンクになっているか
- [ ] 未決事項を空欄で放置していないか
- [ ] `INDEX.md` を更新したか

**目視チェック（人が判断）**

- [ ] 実装者にコード構造を判断してもらえるか
- [ ] coreの言語非依存設計と矛盾がないか
- [ ] 言語を変えたら書き直しが要る内容になっているか
- [ ] 他の実装設計書と重複した記述がないか

実装設計書を作る前に、一度だけ行う。

- **markdownlint**: `MD041` を `false` にする。理由: 先頭に戻りリンクを置き、見出しが1行目にないため。設定は `.markdownlint-cli2.jsonc` に置く。
- **確認**: `markdownlint-cli2` でエラーがないことを確かめる。
