# 設計書運用ガイドライン

> **目的**: 言語非依存の詳細設計を、言語固有のコード構造へ写像する実装設計を運用し、AIと人間の開発効率を高める。
> **前提**: 実装設計は詳細設計（core）の判断をコード構造に翻訳する場所であり、設計の根拠や業務判断は書かない。

## 2. 書くことと書かないこと

実装設計にはコード構造の判断を書く。業務判断と業務上の根拠は書かない。技術選定の理由・代替案・トレードオフは書く。

| 書くこと | 書かないこと |
| :--- | :--- |
| モジュール・パッケージ構成 | 業務上の判断と、その基準 |
| クラス・関数の割り当て（公開境界） | 判断の基準を選んだ根拠（業務レベル） |
| フレームワーク・ライブラリの選定と、その理由・代替案 | 境界の値と、その値の根拠 |
| 具体アダプタと配線（composition root、DI） | 状態と、変わるきっかけ |
| 言語非依存設計から実装への写像 | DSLの文法規則 |
| 言語固有の制約と、その対処 | I/O分離の境界の定義 |
| 設定・エラー変換・DB/API名 | 業務上の状態遷移 |
| 非機能の実現手段（性能、安全、監視） | 非機能の目標値 |
| ビルド・テスト構成 | |

- **見分け方**: 言語を変えたら、この文書を書き直す必要があるか。必要なら実装設計の話。不要ならcoreへ移す。
- **状態の呼び方**: 用語集の語で書く。識別子は命名規約に従う。

## 2.1 写像表（必須）

各実装設計書には、言語非依存設計から実装への写像を表で示す。

| core ID（節） | specs ID | モジュールパス | 公開入口 | 実装状態 | 検証方法 |
| :--- | :--- | :--- | :--- | :--- | :--- |

- **実装状態**: `実装済` / `未実装` / `対象外` のいずれかを書く。未実装と対象外は明示的に残す。
- **core IDの網羅**: `impl/{lang}/INDEX.md` で、参照すべきcore IDの網羅率を確認する。
- **検証方法**: テスト名、ゴールデンケース、または手動確認のいずれかを書く。

## 3. 分量の上限

ファイルが太るのを、読んだ印象ではなく行数で止める。

| 種別 | 目安 | 上限 | 超過時の対応 |
| :--- | :---: | :---: | :--- |
| 実装設計書 | 150行 | 250行 | モジュール単位で分割する |

- **測定**: `wc -l impl/**/*.md` で確認する。
- **原則**: 上限を超えたら「書きすぎ」ではなく「分割漏れ」と考える。
- **対象外**: 本ガイドライン、`INDEX.md`、用語集（`DEF-000`）。

---

## 4. 粒度の決め方

- **単位**: 1つのモジュールまたは1つのサブシステムを1ファイルとする。
- **見分け方**: そのファイルだけを実装者に見せて、コード構造を判断してもらえるか。
- **大きすぎのサイン**: 概要が「〜と〜を行う」と接続詞でつながる。
- **細かすぎのサイン**: 単独では意味をなさず、他と必ずセットで読む。

---

## 5. 基本方針

実装設計は、core（詳細設計）の言語非依存判断を、言語固有のコード構造に写像する層。

| 種別 | 配置先 | 主な役割 | 記述しないこと |
| :--- | :--- | :--- | :--- |
| 実装設計書 | `impl/` | モジュール構成、クラス割り当て、フレームワーク選定 | 業務判断、I/O分離の境界定義 |

- **coreとの関係**: coreの方式設計書（ARC）・インターフェース設計書（INT）・DSL仕様書（DSL）を前提とする。写像の根拠としてIDで参照する。
- **specsとの関係**: specsの画面・業務仕様を実装に落とし込む際の制約として参照する。
- **言語の選定**: 実装設計書群は言語ごとに `impl/{lang}/` に分ける。1つのディレクトリに複数言語を併記しない。
- **複数アプリ**: 同一言語で複数アプリがある場合は `impl/{lang}/{system}/` に分割する。IDの連番と `INDEX.md`・`DEF-000` は `{system}/` 単位で持つ。`impl/{lang}/INDEX.md` は全システムの索引とする。

---

## 6. ファイル命名規則

- **実装設計書**: `impl/{lang}/IMP-{3桁数字}_{モジュール名}.md`
- **用語集**: `impl/{lang}/DEF-000_用語集.md`（言語ディレクトリ直下に固定）

- **ID指定**: 3桁の連番（`001`, `002`, ...）を使用する。連番は言語ディレクトリごとに独立する。
- **予約ID**: `DEF-000` は用語集に固定する。他に割り当てない。
- **区切り文字**: IDと名称の間はアンダースコア `_` で区切る。
- **ファイル名**: スペースを含めず、実装者に通じる日本語の名詞にする。
- **ID再利用の禁止**: 廃止したIDは欠番のまま残し、新しく割り当てない。

## 7. ディレクトリ構造

```
impl/
├── INDEX.md                  # 全言語の実装設計書の一覧
├── {lang}/                   # 言語ごとの実装設計書群
│   ├── INDEX.md              # その言語の実装設計書の一覧
│   ├── DEF-000_用語集.md     # その言語の技術用語集
│   ├── IMP-001_モジュール構成.md
│   ├── ...
│   ├── res/
│   │   ├── uml/
│   │   │   └── svg/
│   │   └── mmd/
│   │       └── svg/
│   └── archive/
└── archive/                  # 廃止済み言語群
```

- **図・画像**: 配置ルールは `docs/COMMON.md` §3 を参照。impl 固有の配置先は `impl/{lang}/res/`。
- **INDEXの必須化**: `impl/INDEX.md` と各言語ディレクトリの `INDEX.md` を必ず置く。`impl/INDEX.md` は全言語・全システムの索引とする。
- **取り込み**: 本文には SVG を画像で参照する。
- **変換**: ソースを直したら SVG を作り直す。SVG を直接直さない。
- **作る範囲**: 実際にファイルを置く場合にだけ `res/` を作る。空のまま用意しない。

## 8. 参照ルール

- **IMP → core (ARC / INT / DSL)**: 写像の根拠となる方式・境界・文法をIDで参照する。参照は `docs/COMMON.md` §4 のリンク形式に従い、IDと相対パスを併記する（例: `[ARC-001](../../core/arch/ARC-001_...md)`）。節番号は任意。
- **IMP → specs (SCR / BIZ)**: 実装対象の画面・業務仕様をIDで参照する。参照は `docs/COMMON.md` §4 のリンク形式に従う。
- **IMP → 言語AGENTS.md**: コーディング規約・命名規則の根拠を参照する。
- **core → IMP**: 書かない。詳細設計は実装の有無に左右されない。
- **specs → IMP**: 書かない。基本設計は実装の有無に左右されない。

共通の参照ルールは `docs/COMMON.md` §4 を参照。

## 9. 変更・廃止の運用

共通ルールは `docs/COMMON.md` §5 を参照。impl固有の追加事項:

- **順序**: 実装を変えるときは、実装設計書を先に直す。設計書（core / specs）の変更が必要なら、そちらを先に直す。
- **影響の確認**: core/specs は impl を参照しない。impl 側の影響は `grep -r "対象ID" impl/` で確認する。
- **言語の変更**: 言語を変えるときは `impl/{lang}/` を新規作成する。既存の言語群は `impl/archive/` へ移す。
- **変更トリガー**: モジュール境界、依存方向、公開契約、DI、フレームワークが変わったときのみ実装設計書を更新する。内部リファクタは対象外。
- **状態ゲート**: 参照するcoreまたはspecsが `検討中` の間、impl を `確定` にしない。確定済みのimplが参照先の変更で `検討中` に戻る場合は、impl/INDEX.md に波及を記録する。
- **アーカイブ先**: 個別文書は `impl/{lang}/archive/`、言語群全体は `impl/archive/`。言語群を移す場合は、内部の `INDEX.md`・`DEF-000`・相対リンクを更新する。

## 10. 言語非依存設計との境界

実装設計に書いてよいものと、coreへ書くべきものの境界。

- **実装設計に書く**: モジュール名、クラス名、関数名、フレームワーク名、ライブラリ名、ビルドツール名、ディレクトリ構成、依存関係、具体アダプタと配線（composition root、DI）、設定、エラー変換、DB/API名、非機能の実現手段。
- **coreに書く**: I/O分離の境界、決定論の守り方、DSLの文法規則、乱数・時間の扱い方の判断基準。
- **見分け方**: 「TypeScriptからRustに変えた場合、この文書を直す必要があるか」を問う。直す必要があるなら実装設計。不要ならcore。

- **根拠の扱い**: 業務判断の根拠は書かない。技術選定の理由・代替案・トレードオフは書く。詳細な比較検討は ADR に委ねる。
- **ADR**: `impl/{lang}/adr/ADR-{3桁数字}_{名称}.md` に記録する。IDの連番は言語ディレクトリごとに独立する。
- **言語AGENTS.md**: ルートの `{言語名}.md`（例: `Typescript.md`）を参照する。
- **非機能の役割分担**: 目標値はspecs、方式はcore、実現手段はimpl。
