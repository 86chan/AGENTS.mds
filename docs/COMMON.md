# 共通運用ガイドライン

> **目的**: 設計書・仕様書・実装設計書に共通する記述ルールと運用ルールを1箇所に集約する。
> **前提**: 本ファイルのルールは `core/` `specs/` `impl/` のすべてのガイドラインに適用する。各層のガイドラインは差分のみを書く。
> **適用除外**: 本ファイル自身（`COMMON.md`）および各層のガイドライン（`Core.md` 等）は、文書状態・決定者・未決事項・先頭/末尾リンクの記載対象外とする。

---

### 0 ツール一覧

使うツールと入手先を並べる。ドキュメントを整備するためのツールのみを扱う。

* **PlantUML**: JS 版の `@plantuml/core` を使う。
  * 用途: `.uml` を SVG に変換する。
  * 入手先: [PlantUML core](https://www.npmjs.com/package/@plantuml/core)
* **Mermaid**: `@mermaid-js/mermaid-cli` を使う。
  * 用途: `.mmd` を SVG に変換する。
  * 入手先: [Mermaid CLI](https://www.npmjs.com/package/@mermaid-js/mermaid-cli)
* **markdownlint**: `markdownlint-cli2` を使う。
  * 用途: 記述ルールを機械で確かめる。
  * 入手先: [markdownlint-cli2](https://www.npmjs.com/package/markdownlint-cli2)
* **jsonschemalint**: `@sourcemeta/jsonschema` を使う。
  * 用途: JSON Schemaを機械で確かめる。
  * 入手先: [JSON Schema CLI](https://www.npmjs.com/package/@sourcemeta/jsonschema)

## 1. 記述の鉄則（全ドキュメント共通）

* **長文の禁止**: 1文あたり80文字前後を超える文章は禁止する。
  * **カウント基準**: 全角・半角を問わず1字1文字と数える。
  * **対象外**: 表のセル、コードブロック、URLを含む行は数えない。
* **箇条書きの徹底**: 複雑な説明は段落にせず、箇条書きで表現する。
* **簡潔な表現**: 主語と述語を明確にし、冗長な装飾語は削る。
* **重複の禁止**: 同じ規約を2ファイルに書かない。3ファイル以上に同じ記述が出たら共通仕様書へ移す。
* **参照の優先**: 他文書の内容は再掲せず、IDとリンクで参照する。

### 1.1 共通の記載事項

* **先頭**: 1行目に `[一覧へ戻る](相対パス)` を置く。
* **区切り**: 先頭リンクの後に空行、`---`、空行を置く。
* **見出し**: `# [ID] 名称` の形で書く。
* **冒頭**: 見出しの後に空行を置き、文書状態を書く（`確定` または `検討中`）。
* **末尾**: `---`、空行、戻りリンクの順で文書を終える。
* **日付**: 文書に書かない。更新日はGitの履歴で追う。
* **決定者**: その決めごとを決めた部門または担当を書く。
* **未決事項**: 決まっていない論点は明記する。空欄のまま残さない。
* **構成**: 見出しは書く内容に合わせて立てる。定型の雛形は用意しない。

### 1.2 使う言葉

* **語彙の出どころ**: 用語集（`DEF-000`）に載っている言葉から選ぶ。
* **造語の禁止**: 辞書にない熟語を作らない。漢語を3つ以上つなげない。
* **和語の優先**: 和語で言えることをカタカナ語にしない。
* **カタカナ語の制限**: 業務で口に出して使う言葉だけ許す。3語続いたら書き直す。
* **言い換えの禁止**: 担当者が「返品」と呼ぶものを「返送処理」と書かない。
* **冗長表現の削除**: 「〜という形で」「〜に関して」「〜の観点から」を消す。
* **短縮**: 「〜することができる」は「〜できる」と書く。
* **記号**: 全角ダッシュ（——）は使わない。カッコか読点に置き換える。

**言い換え表**

| 使わない             | 使う            |
| :------------------- | :-------------- |
| 具備する / 保持する  | 持つ / 備える   |
| 実施する / 遂行する  | 行う            |
| 〜を担保する         | 〜を守る        |
| 〜を勘案する         | 〜を考える      |
| 当該〜               | この〜 / その〜 |
| 〜における           | 〜での          |
| 保守性向上化         | 直しやすくする  |
| ユーザー体験の最適化 | 使いやすくする  |
| 逸脱ケース           | 例外            |
| 恒常的に             | いつも / 常に   |

* **確認方法**: 業務担当者に声に出して読んでもらい、引っかかる語を書き直す。

* **impl への適用除外**: impl 層は技術用語（フレームワーク名、モジュール名、ライブラリ名等）を必須語彙とする。カタカナ語の制限・造語禁止・和語優先は impl には適用しない。

## 2. 用語集（DEF-000）の運用ルール

用語集は設計書として持つ。本ガイドラインには用語を書かない。

* **位置づけ**: 最初に作る設計書。他の設計書より先に作る。
* **場所**: 各層の直下に `DEF-000_用語集.md` を置く。IDは `000` で固定する。
* **載せるもの**:
  * 業務の言葉（会員ランク、返品、締め日など）。
  * 業務上の状態の呼び名（有効、ロック中など）。
  * 設計書を書くための言葉（決めごと、判断の基準、根拠など）。
  * 文書状態の値（`確定`、`検討中`）。この2語以外を文書状態に使わない。
* **載せないもの**:
  * 実装の名前（テーブル名、クラス名、API名）。
  * 国語辞書で足りる一般語。
* **impl への例外**: `impl/{lang}/DEF-000_用語集.md` は技術用語集として、フレームワーク名・モジュール名・ライブラリ名・設定キー等を載せる。この場合「実装の名前を載せない」は適用しない。載せる語の種類は Impl.md に定義する。
* **1語の書式**: 用語、定義、使わない言い換え、の3列で書く。
* **使わない言い換え**: 同じものを指す別名を必ず書く。これが表記ゆれの歯止めになる。
* **機械可読の維持**: 「使わない言い換え」の列は禁止語チェックの元にする。書式を崩さない。
* **追加のタイミング**: 新しい言葉を使う前に用語集へ足す。設計書の中で定義しない。
* **行数上限**: 対象外とする。分割せず1ファイルで持つ。
* **廃止**: 廃止しない。使わなくなった語は「使わない言い換え」に残す。

### 2.1 作成手順（AIに用語集を作らせるとき）

1. 業務担当者の議事録、既存の資料・画面、問い合わせ文面から言葉を拾わせる。
2. 同じものを指す別名をまとめさせ、どれを使うか担当者に決めてもらう。
3. 決まった語を用語集に、残りを「使わない言い換え」の列に入れる。
4. 以降の設計書作成では、用語集を必ず添えて渡す。

## 3. 図・画像の扱い

画像やUML図など、Markdown以外のファイルの置き場所と取り込み方を定める。

* **置き場所**: 種別ごとのディレクトリ直下に `res/` を作って置く。
* **共通図**: 複数種別で使う図は `common/res/` に置く。
* **画像**: `res/img/` に置く。
* **図ソース**: 図は形式ごとの場所に1図1ファイルで置く。
  * PlantUML は `res/uml/` に置く。ファイルは `{図の概要}.uml`。
  * Mermaid は `res/mmd/` に置く。ファイルは `{図の概要}.mmd`。
* **変換後の図**: ソースと同じ形式の場所に SVG を置く。
  * PlantUML は `res/uml/svg/`。
  * Mermaid は `res/mmd/svg/`。
* **取り込み**: 本文には SVG を画像で参照する。
  * 例: `![状態遷移](res/uml/svg/state_flow.svg)`
* **変換**: ソースを直したら SVG を作り直す。SVG を直接直さない。
* **分割の原則**: 図は必ず別ファイルにする。Markdown本文へ図の定義を直接書かない。
* **作る範囲**: 実際にファイルを置く種別にだけ `res/` を作る。空のまま用意しない。
* **参照パス**: 相対パスで書く。
* **ファイル名**: 設計書のIDに合わせなくてよい。図の中身が分かる名前を付ける。

## 4. 参照ルール（共通）

* **全設計書 → INDEX**: 先頭と末尾に戻りリンクを置く。
* **INDEX → 各設計書**: 各行のIDを `[ID](相対パス)` でリンクする。
* **用語集への参照**: 個別には書かない。全設計書に当然に適用する。
* **循環参照**: 同一層内の関連列挙に限り許す。層をまたぐ参照（specs→core→impl）は一方向とする。
* **禁じるのは重複だけ**: 同じ内容が2箇所にあると、片方が古くなる。
* **リンク形式**: `[表示文字](相対パス)` で書く。
  * `![]()` は画像の表示に使い、リンクには使わない。
  * 相対パスを使い、パスをコードで囲まない。

### 4.1 逆引き（INDEX.md）

* **役割**: どの設計書がどの決めごとを使うかを1枚で管理する。
* **主語の固定**: 1行を1設計書とする。関連する他の設計書IDを関連IDに列挙する。
* **リンク**: 各行のIDを `[ID](相対パス)` で設計書へリンクする。
* **形式**: ID、名称、文書状態、関連IDの列とする。
* **更新**: 新規作成、廃止、名称変更のたびに更新する。

## 5. 変更・廃止の運用

### 5.1 変更

* **順序**: 仕様を変えるときは、コードより先に設計書を直す。
* **影響の確認**: 直す前に `grep -r "対象ID"` と `INDEX.md` で関連を調べる。
* **言葉の変更**: 呼び名を変えるときは用語集を先に直し、旧称を「使わない言い換え」へ移す。
* **実装都合の変更**: コードの構成を変えただけでは core / specs の設計書を触らない。impl は Impl.md §9 の変更トリガーに従う。触る必要が出たら粒度を疑う。

### 5.2 廃止

廃止は文書状態では表さない。アーカイブへ移すことで表す。

1. `INDEX.md` で関連が0件であることを確認する。併せて `grep -r "対象ID"` で被参照がないことを確認する。
2. ファイルを `archive/` へ移す。
3. `INDEX.md` から該当行を消す。

* **IDの扱い**: 欠番のまま残し、使い回さない。
* **用語集**: 廃止しない。使わなくなった語は「使わない言い換え」に残す。

## 7. レビューチェックリスト（共通）

設計書の変更後、マージ前とチェック前に `markdownlint-cli2`, `@sourcemeta/jsonschema` を実行する。
エラーを直し、自動判定できない項目を目で確認する。

- [ ] 行数が上限内か（`wc -l`）
- [ ] 1文が80文字以内か（表・コード・URL行を除く）
- [ ] 用語集の「使わない言い換え」が混ざっていないか（`DEF-000` から禁止語を生成し `grep`）
- [ ] 関数名、テーブル名、API名が混ざっていないか（`()` や camelCase を検出）
- [ ] 図を本文に直書きせず、SVG を画像で参照しているか
- [ ] 文書状態が `確定` / `検討中` のどちらかか
- [ ] 各設計書の先頭と末尾に INDEX へのリンクがあるか
- [ ] INDEX の各行が設計書へのリンクになっているか
- [ ] 未決事項を空欄で放置していないか
- [ ] `INDEX.md` を更新したか

**目視チェック（人が判断）**

- [ ] 用語集に載っていない言葉を使っていないか
- [ ] 新しく使った言葉を用語集へ足したか
- [ ] 辞書にない造語や、業務で使わないカタカナ語がないか
- [ ] 他の設計書と重複した記述がないか

層固有のチェック項目は各層のガイドライン §11 を参照。
