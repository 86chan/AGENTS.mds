# 設計書運用ガイドライン

> **目的**: 画面仕様と業務仕様を分離し、AIと人間の開発効率を高める。
> **前提**: 設計書は業務の決めごとを書く場所であり、実装の設計図ではない。

## 2. 用語集（DEF-000）

運用ルールは `docs/COMMON.md` §2 を参照。specs固有の追加事項:

* **場所**: `specs/DEF-000_用語集.md`。specs直下に置く。IDは `000` で固定する。
* **載せる語の種類**: 業務の言葉、業務上の状態の呼び名、設計書を書くための言葉、文書状態の値。
* **載せないもの**: 実装の名前（テーブル名、クラス名、API名）、国語辞書で足りる一般語。

---

## 3. 書くことと書かないこと

設計書には概念レベルの決めごとを書く。実装の手順は書かない。

| 書くこと                 | 書かないこと                |
| :----------------------- | :-------------------------- |
| 業務上の判断と、その基準 | 関数名、引数、戻り値        |
| その基準を選んだ根拠     | テーブル名、カラム名、API名 |
| 境界の値と、その値の根拠 | 条件分岐の順序、データ構造  |
| 例外の扱い               | エラーコード、ログ出力形式  |
| 状態と、変わるきっかけ   | クラス構成、実装の分け方    |

* **見分け方**: 実装のやり方を変えても、仕様書の書き直しが要らないか。
* **状態の呼び方**: 用語集の語で書く。コード上の定数名に合わせない。
* **図の線引き**: 業務レベルの状態遷移図は書いてよい。ER図など実装寄りの図は書かない。

### 3.1 記述例

**NG（実装レベル）**

```text
calculateDiscount(rank, amount) を呼び出す。
rank が "GOLD" の場合、amount * 0.9 を返す。
```

**OK（概念レベル）**

```text
* ゴールド会員には10%の割引を適用する。
  * 根拠: 年間20万円以上の購入を続けてもらうための優遇。
  * 併用: 金額による割引と重ねて適用してよい。
```

## 4. 分量の上限

ファイルが太るのを、読んだ印象ではなく行数で止める。

| 種別       | 目安  | 上限  | 超過時の対応                            |
| :--------- | :---: | :---: | :-------------------------------------- |
| 画面仕様書 | 150行 | 250行 | 決めごとをBIZへ切り出す／画面を分割する |
| 業務仕様書 | 100行 | 200行 | 決めごとの単位で分割する                |
| 共通仕様書 | 200行 | 300行 | 分類を細かく分ける                      |

* **測定**: `wc -l specs/**/*.md` で確認する。
* **原則**: 上限を超えたら「書きすぎ」ではなく「分割漏れ」と考える。
* **例外**: 分けると意味が壊れる場合のみ、冒頭に理由を1行で書く。
* **対象外**: 本ガイドライン、`INDEX.md`、用語集（`DEF-000`）、`.uml` `.mmd` `.svg` などの図ファイル。

## 5. 粒度の決め方

### 5.1 画面（SCR）

* **単位**: 利用者が1つの画面と認識する単位ごとに、1ファイルとする。
* **Web画面**: 原則として、URLで直接開ける単位を1画面とする。
* **URL中の値**: 注文番号などの値が違うだけなら、同じ画面とする。
* **表示条件**: URLの検索条件や表示条件が違うだけなら、同じ画面とする。
* **モーダル・タブ**: 原則として親画面に含める。
* **分けてよい場合**: 単独の業務目的を持つ場合だけ、別画面として扱う。

### 5.2 決めごと（BIZ）

* **単位**: 業務担当者が「1つの決めごと」と認識するまとまり。
* **見分け方**: そのファイルだけを担当者に見せて、合っているか判断してもらえるか。
* **大きすぎのサイン**: 概要が「〜と〜を行う」と接続詞でつながる。
* **細かすぎのサイン**: 単独では意味をなさず、他と必ずセトで読む。
* **注意**: 実装の分け方に合わせない。コードの構成が変わっても分け直さない。

## 6. 基本方針

画面（UI）、業務の決めごと、全体規約の3層で管理する。

| 種別           | 配置先           | 主な役割                           | 記述しないこと           |
| :------------- | :--------------- | :--------------------------------- | :----------------------- |
| **画面仕様書** | `specs/screens/`  | UI/UX、レイアウト、表示制御、遷移  | 決めごと、データの扱い   |
| **業務仕様書** | `specs/business/` | 決めごと、判断の基準、状態、例外   | デザイン情報、実装の手順 |
| **共通仕様書** | `specs/common/`   | 全体規約、共通の表示ルール         | 個別の画面・業務の事情   |

* **共通仕様書に置くもの**: 入力チェックの書式、エラー表示の統一ルール、権限の区分、日付や金額の書き方。
* **用語集の扱い**: 内容は共通層に属するが、ファイルは `specs` 直下に固定で置く（§2）。
* **移す目安**: 3ファイル以上に同じ記述が出たら共通仕様書へ移す。

## 7. ファイル命名規則

### 7.1 フォーマット

* **画面仕様書**: `SCR-{3桁数字}_{画面名}.md`
* **業務仕様書**: `BIZ-{3桁数字}_{業務名}.md`
* **共通仕様書**: `COM-{3桁数字}_{分類名}.md`
* **用語集**: `DEF-000_用語集.md`

### 7.2 命名ルール

* **ID指定**: 3桁の連番（`001`, `002`, ...）を使用する。
* **予約ID**: `DEF-000` は用語集に固定する。他に割り当てない。
* **区切り文字**: IDと名称の間はアンダースコア `_` で区切る。
* **ファイル名**: スペースを含めず、業務で通じる日本語の名詞にする。
* **動詞の回避**: 「〜処理」「〜判定」より「〜ルール」「〜基準」を選ぶ。
* **ID再利用の禁止**: 廃止したIDは欠番のまま残し、新しく割り当てない。
* **例**:
  * 画面: `SCR-001_ログイン画面.md`
  * 業務: `BIZ-001_アカウントロック基準.md`
  * 共通: `COM-001_入力チェック規約.md`

```text
specs/
├── INDEX.md          # 全仕様書の一覧と関連（逆引き）
├── DEF-000_用語集.md  # 用語集（specs直下に固定）

│           └── svg/  # 変換した図 (.svg)
```

## 9. 参照ルール

* **SCR → BIZ / COM**: 関わる決めごとと規約をリンクで並べる。
* **BIZ → BIZ / COM**: 制限しない。ただし内容の再掲は禁止する。
* **BIZ → SCR**: 書かない。決めごとは画面の有無に左右されない。

共通の参照ルールは `docs/COMMON.md` §4 を参照。

### 9.1 逆引き（INDEX.md）

`docs/COMMON.md` §4.1 を参照。主語は1画面（SCR）とし、関連するBIZ・COMを関連IDに列挙する。画面の表は画面ID、画面名、文書状態、関連ID（BIZ/COM）の4列。

## 11. レビューチェックリスト

共通のチェック項目は `docs/COMMON.md` §5 を参照。以下は specs 固有.

仕様書の変更後、マージ前とチェック前に `markdownlint-cli2` を実行する。
エラーを直し、自動判定できない項目を目で確認する。

- [ ] 行数が上限内か（`wc -l`）
- [ ] 1文が80文字以内か（表・コード・URL行を除く）
- [ ] 用語集の「使わない言い換え」が混ざっていないか（`DEF-000` から禁止語を生成し `grep`）
- [ ] 関数名、テーブル名、API名が混ざっていないか（`()` やcamelCaseを検出）
- [ ] 図を本文に直書きせず、SVG を画像で参照しているか
- [ ] 文書状態が `確定` / `検討中` のどちらかか
- [ ] 各設計書の先頭と末尾に INDEX へのリンクがあるか
- [ ] INDEX の各行が設計書へのリンクになっているか

**目視チェック（人が判断）**

- [ ] 用語集に載っていない言葉を使っていないか
- [ ] 新しく使った言葉を用語集へ足したか
- [ ] 辞書にない造語や、業務で使わないカタカナ語がないか
- [ ] 業務担当者が読んで、合っているか判断できるか
- [ ] 判断の基準に、その値を選んだ根拠が書かれているか
- [ ] 画面仕様書に決めごとが混ざっていないか
- [ ] 業務仕様書にUI情報が混ざっていないか
- [ ] 他の仕様書と重複した記述がないか
- [ ] 未決事項を空欄で放置していないか
- [ ] `INDEX.md` を更新したか
